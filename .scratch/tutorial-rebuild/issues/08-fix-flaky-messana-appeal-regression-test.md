# 08 — Fix flaky evt-messana-appeal regression test

**What to build:** `__tests__/tutorialWorldFreeze.test.ts`'s "world freeze — random events and war ignition › not frozen: the same ignition-eligible state forces evt-messana-appeal (regression guard)" test intermittently fails — observed directly during a `pre-push` run (full `npm test`), not a hypothetical. Make it deterministic.

**Root cause (verified, not assumed):** the test's `UNFROZEN` tutorial state (`activeArc: null`) leaves every `WorldGateCategory` open, including `foreignWarDeclarations`. `cityEngine.checkForeignWarDeclarations` runs earlier in `processSeason` than step 12's event injection, and only requires a foreign city to be at `getRelationshipTier` `'hostile'` (score `<= 15`, `models/city.ts:265`) to roll an unconditional `AI_DECLARE_WAR_CHANCE = 0.08` (`cityEngine.ts:497`) chance of declaring war that season — Carthage's `owner: 'carthage'` maps it to `enemyId: 'carthage'` via `getForeignWarTargetEnemyId` (`cityEngine.ts:459-461`). Carthage's own `startingRelationship` is exactly `15` (`data/cityDefinitions.ts:356`) — i.e. it starts the game already sitting AT the hostile threshold, not drifting toward it. So on ~8% of runs, `checkForeignWarDeclarations` adds a `{ enemyId: 'carthage', ... }` entry to `s.wars` before step 12 ever runs; step 12's forced-injection guard for `evt-messana-appeal` (`turnSequencer.ts:1928`) requires `!(s.wars ?? []).some(w => w.enemyId === 'carthage')`, so that guard now reads false and the branch is skipped — the event never fires, and the test's `expect(...).toBe(true)` fails.

This is pre-existing and unrelated to any of tickets 01-07's own changes — confirmed by reproducing it against the tutorial-rebuild branch's pre-ticket-05 commit too. It reproduces more easily than one might expect (~1-in-8 to ~1-in-13 runs in repeated local sampling) because the 8% roll needs no drift or luck beyond Carthage's own starting value.

**Blocked by:** None — standalone bugfix, no dependency on any beat.

**Status:** ready-for-agent

- [ ] The "not frozen: forces evt-messana-appeal (regression guard)" test passes deterministically (verified: 50+ consecutive local runs, or the roll is removed from the test's control flow entirely — not just statistically unlikely to fail).
- [ ] The fix is scoped to this one test's setup, not a change to `checkForeignWarDeclarations`, `AI_DECLARE_WAR_CHANCE`, or Carthage's `startingRelationship` — those are real game balance/behavior, not test bugs, and are out of scope here.
- [ ] The "frozen: no evt-messana-appeal is injected" test (the pair this one sits next to) and the file's other `foreignWarDeclarations` describe block (which already deliberately overrides Carthage's `relationshipScore` for its own purposes) are left passing and are not weakened.
- [ ] No other test in the suite that relies on `UNFROZEN`/`activeArc: null` fixtures is silently carrying the same flake — grep for other `processSeason` calls against an unfrozen/null-arc state with default `cities` and check each one against this same root cause before closing the ticket.

**Implementation note:** the simplest fix is almost certainly to give this specific test's `makeState` a `cities` override that keeps every foreign power out of `'hostile'` tier (mirroring the pattern the file's own "world freeze — foreign war declarations" describe block already uses in the other direction — it explicitly sets `relationshipScore: 5` to force hostility; this test wants the opposite, something like `relationshipScore: 50` on Carthage, or on whichever cities are `status: 'foreign'` in `INITIAL_STATE`). Mocking `Math.random` instead is a live option too, but riskier here: this same `processSeason` call has several other unseeded rolls in flight (bill resolution, crisis drift, etc.) that a blanket `Math.random` mock could distort in ways the test doesn't intend to assert on — an explicit city-state override is more surgical and easier to reason about.
